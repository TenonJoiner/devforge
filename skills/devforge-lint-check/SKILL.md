# devforge-lint-check — 编译检查与 Lint 分析

## 概述

编译通过（零 warning）→ Lint 分析（工具化静态检查）。两层防护，提前拦截问题。

本 skill 是项目 lint 脚本的调度器——**不自行拼凑 lint 参数，不根据 git diff 自行筛选文件**。具体查什么、怎么查由项目自己的构建/lint 脚本决定，skill 只负责根据当前模式选择调用哪条命令。

默认只检测并输出报告。带 `autofix` 参数时自动派遣 developer 修复并回归检查，最多 5 轮。

## 检查范围

L1 编译步骤不受范围影响，始终使用全量构建命令。

L2 Lint 检查，范围确定优先级：

1. **`diff-range` 参数存在**：直接使用，原样传递给 lint 脚本
2. **`full` 参数存在**：全仓 lint——执行项目 lint 命令，检查全仓
3. **都不传**（默认）：`git diff HEAD` + `git diff --cached`（工作区未提交变更），透传给 lint 脚本

> **代码就绪由调用方负责**：skill 不做 `git checkout`、`git fetch` 等操作。调用方（如 pr-review）负责确保工作目录位于正确的分支上。
> `diff-range` 由调用方注入，skill 不解析、不修改，直接转发给 lint 脚本。

### 路径来源

| 资源 | 来源 | 说明 |
|------|------|------|
| 构建脚本（Makefile、CMakeLists.txt 等） | `--worktree-path` | 和源码结构强耦合，从 MR 分支读取 |
| 源码 | `--worktree-path` | 待检查的代码 |
| Lint 脚本 + 规则配置（`.clang-tidy`、`.golangci.yml` 等） | **CWD**（原始仓库） | 门禁标准由主线定义；脚本和规则配套使用，同源避免兼容性问题 |
| CLAUDE.md、规则文件 | **CWD**（原始仓库） | 纯 AI 指引，和源码解耦 |

**L1 执行模式**：`cd $WORKTREE_PATH && <构建命令>`——构建脚本和源码均在 worktree。
**L2 执行模式**：Lint 脚本从 CWD 执行，通过参数传递 worktree 路径：`<lint 命令> <worktree 路径参数>`。具体参数名（如 `REPO`、`--src-dir` 等）由项目 lint 脚本定义，从 CLAUDE.md 或项目 lint 说明文档中读取。

`--worktree-path` 为空时（本地开发场景），CWD 同时作为上述两类来源，L1/L2 均从 CWD 执行。

## 职责边界

- ✅ Lint 工具执行 + 告警分类（误报/有意为之/历史遗留/需修复）
- ✅ `autofix` 模式下派遣 developer 修复需修复项
- ❌ 不做深度代码审查（语义 bug、架构问题、设计缺陷）→ 归属 `/df:code-review`
- ❌ 不引入 Skill 未定义的检查工具或步骤
- ❌ Lint 零告警时直接通过，不扩展检查范围
- ❌ 禁止使用 `which <tool>` 发现 Skill 未定义的检查工具并自行拼凑命令
- ❌ 禁止根据 git diff 自行筛选文件或拼凑 lint 参数——范围控制由项目脚本负责
- ✅ 允许使用 `which <tool>` 检查已确认的 lint 脚本所需的运行时工具是否可用

## L1：编译检查

> 构建命令和构建脚本从 `--worktree-path` 读取（见路径来源）。

1. **获取构建命令**
   - 从 CWD 的 CLAUDE.md、README、项目 rules、项目构建说明文档（如 `building.md`）中查找已知的构建方法
   - 若未找到，在 `--worktree-path`（提供时）或 CWD 中探测构建系统文件（Makefile、`build.sh`、`CMakeLists.txt`、`go.mod`、`package.json` 等）
   - 自行探测结果需**向用户确认**后再使用。确认后将命令记录到项目上下文中（如 CLAUDE.md 或项目 rules 文件），后续直接读取
       - **阻断规则**：若构建命令来自自行探测且未经用户确认，禁止进入步骤 2。必须使用 `AskUserQuestion` 向用户确认后方可继续
       - 禁止根据变更文件（`git diff`、`git log` 输出）自行推断或拼凑构建命令

2. **逐一执行所有构建命令**，分别捕获完整输出
       - 每条构建命令输出显式重定向到固定路径：`<构建命令> > /tmp/lint-l1-build-<索引>.log 2>&1; echo "EXIT=$?"`，后续分析直接 Read 该路径。禁止依赖 harness 自动持久化（大输出时临时目录可能已被清理）
       - 必须原样执行步骤 1 确定的构建命令，禁止根据变更文件类型自行判断跳过、缩减或替换构建命令
       - **禁止因 L2 的 lint 命令内部触发编译而合并 L1/L2**——即使 lint 脚本（如 Makefile 的 `lint` target 依赖 `build` target）会自动编译，也必须先独立执行 L1 构建命令。两层独立执行，不可合并
       - 禁止在此步骤执行 `git diff`、`git log` 等变更范围分析——L1 的职责是执行构建，不是判断是否需要构建
       - 构建命令的执行范围由 Skill 使用者（通过上下文配置或确认）决定，不由 agent 决定

3. **处理结果**

   | 结果 | `autofix` 未设置 | `autofix` 已设置 |
   |------|-----------------|-------------------|
   | 零 error、零 warning | 通过，进入 L2 | 通过，进入 L2 |
   | 存在 error 或 warning（本次变更引入） | 输出错误/警告清单，结束 | 派遣 developer 修复，修复后回归编译验证，最多 5 轮 |
   | 存在 error，但经确认为预存在问题（非本次变更引入） | 标注原因后继续进入 L2，报告中单独说明预存在错误及证据 | 同左 |

   > **预存在判定标准**：必须通过 `git log` 或 `git blame` 确认该错误在本次变更之前就已存在，并将证据（commit hash）写入报告 L1 说明中。仅凭"看起来不像我改的"等主观判断不能作为预存在依据。若无法确认是否预存在，按本次变更引入处理。

## L2：Lint 分析

> lint 脚本和规则配置从 **CWD**（原始仓库）读取；执行时从 CWD 发起，通过参数传递 worktree 路径（见路径来源）。

1. **获取 Lint 命令**
   - 从 **CWD** 的 CLAUDE.md、README、项目 rules、项目 lint 说明文档（如 `linting.md`）中查找已知的 lint 方法
   - 若未找到，在 **CWD** 中探测可执行 lint 脚本（`ci/`、`scripts/`、`utils/` 下 + Makefile lint target + `package.json` lint script 等）
   - 自行探测结果需**向用户确认**后再使用。确认后将命令记录到项目上下文中（如 CLAUDE.md 或项目 rules 文件），后续直接读取
       - **阻断规则**：若 lint 命令来自自行探测且未经用户确认，禁止进入步骤 2。必须使用 `AskUserQuestion` 向用户确认后方可继续
       - 禁止根据变更文件（`git diff`、`git log` 输出）自行推断或拼凑 lint 命令
   - 若 `diff-range` 已提供，执行 lint 命令时将其原样传递给 lint 脚本；若 `full` 已提供，全仓执行；否则使用默认增量范围（`git diff HEAD` + `git diff --cached`）

   **可执行 lint 脚本 vs 工具配置文件**：

   以下文件是工具规则配置，**不是**可执行 lint 脚本，禁止作为 lint 命令来源：
   - `.clang-tidy`、`.clang-format`
   - `.flake8`、`.pylintrc`、`pyproject.toml [tool.pylint]`
   - `.golangci.yml`
   - `.eslintrc.*`、`.prettierrc.*`

   仅以下类型可视为可执行 lint 脚本：
   - `Makefile` 的 `lint` / `check` target
   - `package.json` 的 `lint` / `check` script
   - 项目根目录或 `ci/`、`scripts/`、`utils/` 下的 `lint.sh`、`lint.py` 等独立脚本
   - `utils/githooks/` 下的 pre-commit hook 脚本

2. **逐一执行所有 Lint 命令**，分别捕获 stdout。若某个命令 stdout 为空，分析对应脚本找到输出重定向的目标文件并读取；仍无法获取则提示用户确认输出位置

   若某 lint 命令因**环境不可用**而失败（缺少依赖、工具未安装、容器镜像不可达等，非代码告警），记录原因后继续执行其余 lint 命令，不阻塞后续流程。

   **所有 lint 命令均零告警时，输出通过信息后结束，不进入步骤 3。**

   2.5 **产出物发现**：Lint 命令执行完毕后，扫描命令的产出（stdout 内容、重定向目标目录、命令日志中记录的输出路径），列出所有产出文件。

   对于每条告警的交叉验证，必须同时获取以下三类信息：

   | 信息类型 | 用途 | 缺失后果 |
   |---------|------|---------|
   | 分级摘要 | 告警级别、文件+行号、规则名 | 无法确定分析优先级 |
   | 精确表达式 | 触发告警的具体源码行、宏展开、fix-it hint | 只能猜测告警指向哪个表达式，误判率极高 |
   | 诊断日志 | stderr 中的编译错误、分析器异常退出信息 | 可能遗漏环境问题导致的假告警 |

   分级摘要和精确表达式可能对应两个不同文件，必须两方交叉比对后再读源码验证。

   若只找到分级摘要而未找到精确表达式，或产出文件用途不明确：
   - 先尝试启发式匹配：文件名含 `summary`/`report`/`lint` → 分级摘要，含 `detail`/`full`/`raw`/`result` → 精确表达式
   - 匹配失败则列出目录下所有文件名，向用户确认各文件的角色（分级摘要/精确表达式/其他），确认后写入项目上下文

3. **分析 Lint 报告**（仅部分 lint 命令存在告警时执行）

   原始 lint 报告存在噪声——告警不一定是真问题，级别也不一定准确。将告警按文件分组后派遣 lint-analyst 并行分析（告警 ≤ 3 条且 ≤ 2 个文件时 agent 自行分析），逐条经**源码 + lint 规则**交叉验证后，**废弃原始报告，按输出格式重写新报告**。禁止在原报告上逐条追加判定标注——必须按分类（需修复/历史遗留/已排除/规则建议）重新组织内容。

   每条告警，lint-analyst 执行以下三步：

   **a. 读源码**：先读取告警对应的精确表达式（含宏展开），确认触发告警的具体表达式；再读取该表达式所在行及上下文，理解代码意图、控制流、值域来源。禁止仅凭行号判定告警指向——必须从精确表达式中找到触发表达式。

   **b. 查规则**：定位触发该告警的 lint 规则（从工具的配置文件如 `.golangci.yml`、`.clang-tidy`、`.eslintrc.*` 中查找），理解规则的设计意图、严重程度定义、已知例外场景。

   **c. 交叉判定**：结合源码上下文和规则意图，逐条产出判定结果（非最终报告）：

   | 判定维度 | 选项 | 说明 |
   |---------|------|------|
   | 是否误报 | 是 / 否 | 告警描述的技术事实是否存在。若代码根本没有告警所指的行为，或工具对当前代码模式存在误判，则为误报 |
   | 是否有危害 | 是 / 否 | 该模式在当前上下文中是否会产生可观测的危害。若为"否"，后续判定无需继续，直接标记为"抑制"——事实存在但不产生危害。验证方法随告警类型不同（类型缩窄→追溯值域上界；空指针→追溯NULL守卫；资源泄漏→分析触发路径可达性），但判据统一为：有危害/无危害 |
   | 危害级别 | CRITICAL / HIGH / MEDIUM / LOW | 仅在"是否有危害=是"时判定。根据危害在源码上下文中的实际影响定级，废弃工具原始级别：CRITICAL=编译失败/运行时崩溃/数据损坏/安全漏洞；HIGH=潜在运行时错误/资源泄漏/并发竞态；MEDIUM=代码异味/可维护性问题；LOW=风格不一致/冗余代码 |
   | 是否需修复 | 是 / 否 | 仅在"是否有危害=是"时讨论。综合考虑危害程度、修复成本、是否为本次变更引入 |
   | 规则是否合理 | 保留 / 屏蔽 / 新增 | 规则本身粒度或适用范围是否有问题——过于宽松应新增补充规则，过于激进或无价值应屏蔽 |

   每条判定必须附**源码依据**（引用具体行）和**规则依据**（引用具体规则名及含义）。

   主会话收集结果，按以下分类汇总到最终报告：

   | 分类 | 处理 |
   |------|------|
   | 需修复 | 保留，输出问题说明和修复建议，级别字段显示危害级别（CRITICAL/HIGH/MEDIUM/LOW） |
   | 历史遗留（需修复但非本次引入） | 保留，标注"历史遗留，不阻塞本次合并"，级别同上 |
   | 抑制（事实存在但无危害） | 排除，注明无危害证据（值域计算/守卫代码行号/路径分析） |
   | 误报 | 排除，注明排除理由和规则依据 |
   | 规则建议 | 追加到报告末尾——仅输出判定为"屏蔽"或"新增"的规则及理由。判定为"保留"的规则不出现在报告中 |

   | 模式 | 行为 |
   |------|------|
   | `autofix` 未设置 | 输出最终报告后结束 |
   | `autofix` 已设置 | 需修复列表为空 → 通过；否则派遣 developer 逐项修复，修复后回归 lint 验证，最多 5 轮 |

## 输出格式

所有模式下，除会话内输出外，必须将报告写入指定路径。若提供了 `report-output-path` 参数则使用该路径；未提供时使用 `/tmp/lint-report-<YYYYMMDD-HHMMSS>.md`。每次执行生成新文件，不覆盖历史报告。

**生成报告前必须先读取模板文件**，按模板的章节结构、占位符和自检清单严格生成。禁止凭记忆或推测格式。模板包含三种输出场景的完整结构（零告警通过 / 存在告警 / L1 失败）。

模板查找（按优先级）：
1. `<skill_base_dir>/templates/lint-report.md`（skill 基础目录由 skill launch 时的 base_dir 确定）
2. `find ~/.claude/plugins/ -name lint-report.md`（兜底定位）
3. 仍未找到 → 报错终止，报两个候选路径供人工确认

**生成报告后必须对照模板末尾的自检清单逐项验证**，全部通过方可视为报告完成。任一项未通过则修正报告后重新验证，直到全部通过。此步骤为硬门控——未执行自检的报告不得输出。

## 出口标准

- [ ] L1 编译通过
- [ ] L2 需修复列表为空
- [ ] `autofix` 模式下修复循环不超过 5 轮
- [ ] 每条告警已完成交叉判定（是否误报 / 是否有危害 / 危害级别 / 是否需修复 / 规则是否合理），判定结果体现在最终分类中
- [ ] 每条告警闭环到确定判定之一：修复 / 抑制 / 误报 / 框架约束 / 噪音，附源码依据（引用具体行）和规则依据（引用规则名及含义）
- [ ] 原始工具告警级别（P0-P4、warning/error 等）未出现在最终报告中，所有级别已转换为 CRITICAL/HIGH/MEDIUM/LOW
- [ ] 禁止输出"待确认""疑似""可能是""需要进一步分析"等未完成状态的结论
- [ ] 信息不足时继续搜索（读更多源码、查更多文件、追溯调用链），直到信息充分可以做出确定判定为止
- [ ] "告警指向不明确"不能作为输出模糊结论的理由——应从精确表达式中找到触发表达式后再判定

## 红旗清单

| 红旗 | 触发条件 | 处理方式 |
|------|---------|---------|
| 🚩 修复死循环 | 5 轮修复后仍有未解决问题 | 停止，输出完整问题清单 |
| 🚩 构建命令未知 | 上下文无记录 + 探测无结果 + 用户无法确认 | 停止，提示用户配置构建命令，禁止自行拼凑 |
| 🚩 Lint 命令未知 | 上下文无记录 + 探测无结果 + 用户无法确认 | 停止，提示用户配置 lint 命令，禁止自行拼凑 |
| 🚩 agent 自行扩展检查范围 | agent 引入 Skill 未定义的检查工具、步骤或 agent 类型 | 停止，回退到 Skill 定义的流程 |
| 🚩 agent 跳过交叉判定 | agent 输出中包含工具原始告警级别（P0-P4、warning/error 等）而非统一级别，或告警缺少源码依据+规则依据 | 驳回 agent 重写，补齐交叉判定 |
| 🚩 agent 自行追加非工具检查 | 报告中出现"静态编码规范检查""逐规则审查"等非 L1/L2 工具产出的章节 | 剔除该章节，重写报告 |
| 🚩 修复引入新问题 | developer 修复后出现新的编译 error | 继续修复循环（消耗轮次），若同时触发 5 轮上限则停止 |
