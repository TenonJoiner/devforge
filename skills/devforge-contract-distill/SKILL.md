# devforge-contract-distill — 模块契约蒸馏

## 概述

本 skill 在代码调整告一段落时由开发者主动调用，回顾生成代码被调整之处，将「预期 vs 生成之差」翻译为模块级契约，沉淀/更新 `docs/contracts/<module>.md`。

## 何时使用

- 用 /opsx:apply 生成代码后，实现经过代码调整才符合预期
- 想在代码调整告一段落时，把代码调整中暴露的隐式契约沉淀下来

## 执行约束

**「改了什么」以 git diff/log 为准（非工作区状态），「为什么改」以主会话推论 + 用户确认为准**。「为什么改」由主会话从交互历史（本会话中讨论/纠正过什么）结合 git diff/log 分析出**推论**，再向用户确认；用户只需确认/纠正，**不依赖其从头口述完整原因**。归因提炼与契约写作/合并均在主会话完成；仅评审派遣独立子 agent（architect-reviewer），保证视角独立。

## 工作流程

### 第 1 阶段：识别代码调整

**步骤 1：确定代码调整范围（git 基点）**

确定调整基点：默认自动检测当前分支与上游的分叉点（`git merge-base HEAD @{upstream}`）；无法自动检测时（无上游分支、detached HEAD）询问开发者。`--base <ref>` 用于显式覆盖（如起算点不是与上游的分叉点）。

```bash
git log <base>..HEAD --oneline   # 判断范围内有无代码调整
```

若范围内无代码调整 → 停止「范围内无代码调整」。

**步骤 2：定性判断——筛出疑似缺契约的代码调整**

先基于对话上下文梳理发生了哪些代码调整、判断每条的原因归属（主会话内部分析，不与用户确认），**筛出疑似缺契约的代码调整清单**。

**模块契约**：模块对调用方的**持久承诺**——接口契约（前置/后置/错误语义）、不变式（并发、所有权、顺序）、边界约定。它是「生成代码时本该有据可依、但没成文」的那部分。

**判据**（三条**同时**满足才算疑似「缺模块契约」）：
1. **层级**：该行为像是模块对调用方的**持久承诺**（跨特性稳定、可复用），而非本次特性的一次性设计
2. **无据**：经查证（design/spec/rules）该行为**无成文依据**，AI 生成时只能猜、猜错被纠正
3. **不可发现**：该设计意图无法从代码检索/阅读发现。能从代码发现的（如已有哪些函数可复用）不写契约——那靠生成时「先检索再实现」的工作方法解决（见分流项·团队资产），否则契约会跟不上代码演进

反问检验：「如果该模块已有一份写明此行为的契约，AI 第一次生成就能做对吗？」像是 → 疑似缺契约。

任一不满足判据 → 记入分流项。按根因分两类（判据：改进 skill/模板/rules/上下文后能否预防）：

**团队资产**（写入反馈文件）：
- **skill/模板缺陷**：模板缺章节、skill 缺校验步骤、生成缺工作方法（如未先检索可复用函数就默认新增）
- **rules 缺失**：本应有全局规则但 rules/ 没有
- **上下文缺陷**：spec/rules 未加载进生成上下文，导致 AI 读错/违反
- **表述模糊**：spec/rules 措辞歧义，AI 无法可靠遵循
- **子系统级契约缺失**：跨仓库接口该有契约（arch-extract-subsystem 职责）

**个人失误**（不落盘）：
- **内容判断错误**：本次 design/spec 该写 B 却写了 A（决策级错误，非框架缺漏）

区分关键：改进 skill/模板/rules/上下文后能否预防？能 → 团队资产；不能（纯属本次内容判断错误）→ 个人失误。

**质量门禁**：若没有任何疑似「缺契约」代码调整 → 停止。

**步骤 3：结合 diff 验证并反推契约定义**

对步骤 2 筛出的每条疑似缺契约代码调整，**有目的地**在 diff 中定位其改动来分析——不必通读全量 diff（可能是多次会话积累的大 diff），只定位该调整对应的改动块。

```bash
git diff <base>          # 含工作区未提交变更
```

对每条疑似代码调整：

1. **定位差值**：在 diff 中找到该代码调整的改动块。差值 X→X'（AI 原先生成的 vs 开发者改成的）即「AI 猜的 vs 应该的」。
2. **验证是否真缺契约**：差值是否证实 AI 基于**无成文的错误假设**生成了 X？若差值显示该行为其实已有成文规定、AI 只是没遵守 → 改判为分流项。
3. **反推契约定义**：X 错在哪——AI 猜错了什么**假设**（如「此函数可并发调用」「返回值不用检查」「此 buffer 由调用方释放」）？把对应的「正确假设」写成契约条目（它当初若被写明，AI 就会照做），按内容归类：
   - 非显然的调用前提 / 错误含义 / 返回值所有权 / 并发重入 / 组合时序 → **接口契约**
   - 模块级并发模型 / 所有权 / 顺序 / 状态 → **不变式**
   - 模块职责边界 → **边界约定**
   - 跨模块交互约定（交互时序 / 协议语义 / 错误与超时传播）→ **依赖交互约定**

### 第 2 阶段：归因模块并确认

**步骤 4：归因模块**

将候选契约按来源代码调整的文件路径聚类，映射到模块（目录/编译单元），并拟定模块名：

1. **聚类粒度（细粒度倾向）**：默认按**能精确覆盖改动文件、且职责独立的最深目录**聚类——改动跨多个职责独立的子目录（如 `src/storage/engine/` vs `src/storage/buffer/`）时**按子目录拆分**，不并入公共父级，避免粗粒度模块随蒸馏累积膨胀且不可拆。
2. **目录派生（命名权威）**：模块名由源码目录路径确定性派生（如 `src/storage/` → `storage.md`、`src/storage/engine/` → `storage/engine.md`）。同一模块在任何人眼里都是同一目录，命名天然收敛；不同开发者蒸馏同一模块会得到**相同文件名**，合并时由 git 冲突强制对齐。
3. **查重（强制）**：写新契约文档前必须 `ls docs/contracts/` 并检查默认分支（`git symbolic-ref refs/remotes/origin/HEAD` 指向的分支）上的已有契约，已有覆盖该模块的契约则复用/扩展，禁止再造别名文件。

模块清单从已有契约文档中生长，**禁止**单独预定义模块清单文档（重复真相源，会腐烂）。

**步骤 5：交互确认（一次）**

内部分析完成后，用 AskUserQuestion 与开发者**一次性确认**，不分多次打断。确认对象：

- 每个模块的候选契约（契约条目 + 类型 + 来源代码调整：文件 + 改了什么 + 为什么改）
- 模块划分与粒度：当存在粒度歧义（可并入 `storage.md`，也可拆为 `storage/engine.md` + `storage/buffer.md`），必须**呈现至少两个粒度方案**及各自影响（如"并入 storage.md 将与既有 12 条共存"），让用户**主动选择**而非被动接受单一提议

模块名称、输出路径、归属分别由步骤 4 的目录派生 + 查重、文件路径聚类确定，无需逐项确认。

**质量门禁**：每条候选契约含「契约条目 + 契约类型 + 来源代码调整」；每个模块含「名称 + 输出路径」。

### 第 3 阶段：写入契约

**步骤 6：写入契约与团队反馈**

主会话按模板把步骤 5 确认的候选契约直接写作/合并进 `docs/contracts/<module>.md`：

1. 读取模板 `skills/devforge-contract-distill/templates/module-contract.md`（写作前 MUST 先读取）
2. 若 `docs/contracts/<module>.md` 已存在，读取现有内容，将新契约条目合并进去（去重、解决冲突，新条目以「修订来源」记录本次代码调整来源）
3. 若不存在，按模板新建

将步骤 2 识别的**团队资产**分流项合并写入 `docs/contracts/_feedback.md`（个人失误不落盘），每条含类别、现象、建议改进点。文件已存在时读取并合并——**同类别同现象条目合并为一条并累计出现次数**（不简单追加），便于识别高频痛点驱动改进优先级。

**质量门禁**：每个模块契约文档含必填章节（模块定位与边界、修订来源），条件章节有对应内容才写、不写占位；反馈条目含类别与建议。

### 第 4 阶段：评审

**步骤 7：派遣 architect-reviewer 评审**

主会话派遣 1 个 devforge:architect-reviewer agent（独立评审）评审 `docs/contracts/<module>.md` 的正确性：

- 契约条目与代码一致性（对照来源代码调整中的实际改动）
- 与既有契约是否冲突、是否需要废弃旧条目
- 契约表述是否可执行（前置/后置/异常语义明确，非空话）

修正循环最多 2 轮（由主会话修正）。契约质量要求：每条契约可被未来生成会话直接引用。

### 第 5 阶段：汇报

**步骤 8：终端汇报**

```
已更新契约：
- docs/contracts/storage.md: +2 条（接口契约 1 / 不变式 1）

团队反馈（已写入 docs/contracts/_feedback.md）：
- <类别> → <建议改进点>
```

## 质量门禁

- 第 1 阶段代码调整清单为空 → 提示「范围内未发现代码调整」，停止
- 第 2 阶段模块映射为空 → 提示「无法映射到模块边界」，停止
- 第 4 阶段契约评审未通过 → 修正后重新评审（最多 2 轮）
